# สรุปประเภทเอกสารและคำถาม Hybrid

ตรวจจากโค้ดวันที่ 30 ตุลาคม 2026 รวมการเพิ่มประเภทตรงตัว T02–T07 (ยังไม่ tune)
แหล่งข้อมูล: `prompts.TYPE_NAMES`, `DOC_TYPE_FIELDS` และ `steps_for_types(..., mode="hybrid")`

ระบบจำแนกเอกสารได้ **20 ประเภท** มีชุด field เฉพาะ **5 ประเภท** และอีก
**15 ประเภท** ยังไม่มีข้อกำหนด field เฉพาะของประเภทนั้น ใช้ชุดเดิมของประเภท
ส่วนประกอบที่พบร่วมกัน หรือชุดพื้นฐานเมื่อไม่มีประเภทใดมีชุดเฉพาะ
Unknown เป็นกรณีจำแนกไม่ได้ ไม่นับเป็นประเภทที่ 21

หน้า User แสดงสถานะตามจริง: **รู้จัก · tune แล้ว** สำหรับ 5 ประเภทที่มีชุดฟิลด์เฉพาะ,
**รู้จัก · ยังไม่ tune** สำหรับอีก 15 ประเภท และ **ไม่รู้จัก** เมื่อไม่มีประเภทตรงตัว
ตารางเทียบประเภทส่วนแรกไม่จับประเภทใกล้เคียงหรือประกอบประเภทแทนรหัสใหม่
ส่วน Hybrid prompts แสดงเฉพาะ 5 ประเภทที่มีชุดเฉพาะ ไม่แสดงชุดพื้นฐานของอีก 15 ประเภทหรือ Unknown

จำนวนคำถามด้านล่างคือคำถามหลักของ Hybrid เมื่อ **Extras ปิด** ไม่รวม OCR,
การจำแนก/แยกเอกสาร, งานตรวจ/ซ่อมตาราง และการถามซ้ำหรือเติม field ที่ขาด
แต่ละกลุ่มคือหนึ่ง request และ field ภายในกลุ่มเดียวกันถูกถามพร้อมกัน
โมเดลที่รองรับอาจประมวลผลหลายกลุ่มขนานกัน หมายเลขกลุ่มไม่ได้บังคับลำดับรัน

## กลุ่มคำถามที่ใช้ร่วมกัน

| กลุ่ม | ถามอะไรพร้อมกัน | Field จริง |
|---|---|---|
| ข้อมูลเอกสาร | ชื่อประเภทที่พิมพ์บนเอกสาร + เลขที่ + วันที่ออก | `document_type`, `document_number`, `issue_date` |
| เลขอ้างอิง PO/GR/RTV | เลขใบสั่งซื้อ/ใบรับสินค้า/ใบคืนสินค้าอ้างอิง | `po_gr_rtv_number` |
| ผู้ขายและผู้ซื้อ | Tax ID + รหัสสาขา + ชื่อสาขา ของทั้งสองฝ่าย รวม 6 field | `seller_tax_id`, `seller_branch`, `seller_branch_location`, `buyer_tax_id`, `buyer_branch`, `buyer_branch_location` |
| ยอดเงินสามช่อง | ยอดก่อน VAT + VAT + ยอดรวม VAT | `subtotal`, `vat_total`, `amount_incl_vat` |
| การชำระเงิน | เลขเอกสารที่ชำระ/อ้างอิง + วันที่จ่าย + เลขเช็ค | `inv_rtv_cnr_number`, `payment_date`, `cheque_number` |
| ยอดคงเหลือ | ยอดคงค้าง + VAT คงเหลือ | `remaining_amount`, `remaining_vat_amount` |

## INVOICE และ CREDIT_NOTE — ประเภทละ 4 คำถาม

1. ข้อมูลเอกสาร 3 field
2. เลขอ้างอิง PO/GR/RTV 1 field
3. ผู้ขายและผู้ซื้อพร้อมกัน 6 field
4. ยอดเงินสามช่อง 3 field

ทั้งสองประเภทถาม 13 scalar field เท่ากัน แต่ข้อกำหนด Mandatory ต่างกัน:
เลข PO/GR/RTV ถูกถามใน CREDIT_NOTE ด้วย แต่ไม่ใช่ field บังคับของประเภทนั้น

## RECEIPT — 4 คำถาม

1. ผู้ขายและผู้ซื้อพร้อมกัน 6 field
2. ยอดก่อน VAT + VAT 2 field (`subtotal`, `vat_total`)
3. การชำระเงิน 3 field
4. ยอดคงเหลือ 2 field

รวม 13 scalar field ชุดหลักนี้ **ไม่ถามชื่อประเภท เลขที่ หรือวันที่ของตัวใบเสร็จเอง**
และไม่ถาม `amount_incl_vat` วันที่จ่ายกับวันที่ออกเอกสารเป็นคนละ field
ชื่อ/รหัสผู้ซื้อและผู้ขายที่เสริมใน User JSON จากหัวข้อ OCR ชัดเจน เป็นขั้นแปลงผล
ภายหลัง ไม่ใช่คำถามเพิ่มใน Hybrid profile นี้

## RTV_SHIP_CREDIT — 3 คำถาม

1. ข้อมูลเอกสาร 3 field
2. ผู้ขายและผู้ซื้อพร้อมกัน 6 field
3. ยอดเงินสามช่อง 3 field

รวม 12 scalar field กำหนดบทบาทตามการขายเดิม: ผู้ขายคือผู้รับสินค้าคืน
ผู้ซื้อคือผู้ส่งสินค้ากลับ กฎล่าสุดเพิ่มการผูกสาขากับบล็อก Tax ID ฝ่ายเดียวกัน
และแยกรหัสร้านออกจากสาขาภาษี จำนวนคำถามยังเป็น 3
ผล benchmark ล่าสุดยังพบสาขาผิด จึงยังไม่ถือว่าปัญหานี้แก้สำเร็จ

## WHT_CERTIFICATE — 6 คำถาม

| กลุ่ม | ถามอะไรพร้อมกัน | Field จริง |
|---:|---|---|
| 1 | เล่มที่ + เลขที่หนังสือรับรอง + ลำดับในแบบ | `book_no`, `certificate_no`, `sequence_no` |
| 2 | Tax ID + ชื่อ + รหัสสาขา + ชื่อสาขา + ที่อยู่ ของผู้จ่ายเงิน | `payer_tax_id`, `payer_name`, `payer_branch`, `payer_branch_location`, `payer_address` |
| 3 | Tax ID + ชื่อ + รหัสสาขา + ชื่อสาขา + ที่อยู่ ของผู้รับเงิน | `payee_tax_id`, `payee_name`, `payee_branch`, `payee_branch_location`, `payee_address` |
| 4 | ตารางรายการเงินได้ | `income_items[]`: `income_type`, `payment_date`, `amount_paid`, `wht_amount` |
| 5 | รวมเงินที่จ่าย + รวมภาษีที่หัก | `total_amount_paid`, `total_wht_amount` |
| 6 | ตัวเลือกอัตราเงินปันผลที่เลือกในแบบ | `dividend_rate_option` |

รวม 16 scalar field และตารางเงินได้ 4 คอลัมน์ รุ่นเดิมแยกข้อมูลตัวบุคคลเป็น
ฝ่ายละ 3 คำถาม จึงรวมทั้งเอกสาร 10 คำถาม รุ่นปัจจุบันเป็นฝ่ายละคำถามและรวม 6
ผู้จ่ายและผู้รับยังแยกกันอยู่คนละ request
แบบ 8 คำถามที่เสนอหลัง benchmark ยังไม่ได้ลงโค้ด

## ประเภทที่ไม่มีชุดเฉพาะและ Unknown — ชุดพื้นฐาน 15 คำถาม

ใช้ scalar field ทั้งหมด 34 field แบ่งเป็น:

| กลุ่ม | ถามอะไรพร้อมกัน |
|---:|---|
| 1 | ชื่อประเภทเอกสาร + เลขที่ + วันที่ออก |
| 2 | เลข PO/GR/RTV อ้างอิง |
| 3 | Tax ID + รหัสสาขา + ชื่อสาขา ของผู้ขายและผู้ซื้อ |
| 4 | ยอดก่อน VAT + VAT + ยอดรวม VAT |
| 5 | เลขเอกสารที่ชำระ/อ้างอิง + วันที่จ่าย + เลขเช็ค |
| 6 | ยอดคงค้าง + VAT คงเหลือ |
| 7 | เล่มที่ + เลขที่หนังสือรับรอง + ลำดับในแบบ |
| 8 | Tax ID + ชื่อผู้จ่ายเงิน |
| 9 | รหัสสาขา + ชื่อสาขาผู้จ่ายเงิน |
| 10 | ที่อยู่ผู้จ่ายเงิน |
| 11 | Tax ID + ชื่อผู้รับเงิน |
| 12 | รหัสสาขา + ชื่อสาขาผู้รับเงิน |
| 13 | ที่อยู่ผู้รับเงิน |
| 14 | รวมเงินที่จ่าย + รวมภาษีหัก ณ ที่จ่าย |
| 15 | ตัวเลือกอัตราเงินปันผล |

กลุ่มพื้นฐานนี้ยังมี scalar field ของ WHT ปนอยู่ แต่ไม่ได้ถามตาราง `income_items`
เพราะตารางนี้ต้องจำแนกว่าเป็น WHT จึงจะถูกถาม การรวมเป็นฝ่ายละ 5 field
ใช้เฉพาะเมื่อประเภทมี `WHT_CERTIFICATE` ไม่ได้ใช้กับกลุ่มพื้นฐานของเอกสารอื่น

ใบวางบิลล้วน (`BILLING_NOTE`) ยังใช้ 15 กลุ่ม แต่มีคำสั่งบทบาทคู่ค้าและยอดวางบิล
เฉพาะ โดยในคำถามใช้ `billing_total` แล้วคืนค่าเข้าช่อง `subtotal` ภายหลัง
ยอดนี้คือยอดวางบิล ไม่ใช่การรับรองว่าเป็นยอดก่อน VAT เสมอ

## เอกสารหลายประเภทและ Extras

- ถ้าฉบับเดียวมีหลายประเภท ระบบรวม field ของประเภทที่มีชุดเฉพาะเข้าด้วยกัน
  และไม่ถาม field ซ้ำ จำนวนคำถามไม่ใช่การบวกจำนวนของแต่ละประเภทตรง ๆ
- `INVOICE + TAX_INVOICE` ใช้ชุด INVOICE: 4 คำถาม
- `RECEIPT + TAX_INVOICE` ใช้ชุด RECEIPT: 4 คำถาม
- ถ้าทุกประเภทที่พบไม่มีชุดเฉพาะ จะใช้ชุดพื้นฐาน 15 คำถาม
- เปิด Extras เพิ่มคำถาม `other_fields` อีก 1 กลุ่ม
- ชุดจำแนก 20 ประเภทนี้เป็นประเภทภายใน OCR/Extraction ไม่ใช่รหัสเอกสาร
  ของ schema User JSON เช่น T01/T04 ซึ่งถูก map ในขั้นแปลงผลภายหลัง
- ดูข้อความ prompt จริงชุดปัจจุบันได้ที่หน้า User → Hybrid prompts

## การเพิ่มประเภท T02–T07: จำแนกเท่านั้น

- เพิ่มประเภทตรงตัวจากหัวเอกสาร ไม่สร้างชนิดใหม่จากความคล้ายคลึงหรือคำว่า “ยกเลิก” ลอย ๆ
- รองรับหัวเอกสารไทย/อังกฤษและหัวเอกสารผสมที่แยกสองบรรทัด
- ชนิดอย่างย่อหรือผสมต้องมีคำที่ระบุส่วนประกอบครบ ชื่อชนิดที่โมเดลเสนอจะตรวจเทียบหัวเอกสารอีกครั้ง
- ผล `doc_types` มีชนิดใหม่ พร้อมชนิดส่วนประกอบเดิมที่ระบุชัดในหัวเอกสาร เพื่อใช้ชุดฟิลด์เดิมต่อ
  เช่น T02 มี `INVOICE_TAX_INVOICE`, `INVOICE`, `TAX_INVOICE` จึงยังใช้ชุด INVOICE เดิม 4 คำถาม
- T03/T06 คงชุด RECEIPT เดิม, T04/T05 คงชุด TAX_INVOICE พื้นฐาน และ T07 ใช้ชุดพื้นฐาน
- ไม่มีการเพิ่ม `DOC_TYPE_FIELDS`, Mandatory, กฎตรวจค่า หรือตารางรายการให้ 6 ชนิดใหม่
- หน้า User แสดง “รู้จัก · ยังไม่ tune” และไม่เพิ่มชนิดใหม่ในตัวเลือก Hybrid prompts
- ยังต้องวัดความแม่นยำด้วยไฟล์จริงและเฉลยจาก User การทดสอบโค้ดไม่ได้แทน benchmark โมเดล
